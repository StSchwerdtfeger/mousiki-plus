# Mousiki Plus 5.1.0 (in progress)

- The **Latin letters** key (`"`, `SHIFT+2` on a German keyboard) now also works in the whole meta data menu, the cover fetch overlay, the fetch videos overlay (both tabs), the Video Option and the big folder overlay (`SHIFT+f`), except while a text field has the keyboard.
- **Video Brightness** (`VideoBrightness=`, 0–100 % in steps of 5, 50 = as it is): Settings → ANIMA/VIZ, the VIDEO SETTINGS overlay (`&`), and per track in the Style Option overlay and the SHIFT+s panel of the big video overlay. A gamma curve: black and white stay, nothing burns out.
- **Faster builds with ccache:** CMake uses ccache when it is installed (`-DMOUSIKI_USE_CCACHE=OFF` switches it off); `setup.ps1` installs it with winget and has `-NoCcache`. A clean rebuild with a warm cache takes seconds instead of minutes.
- **Use mp4 audio for this song** (true / false, default false): for a song that is paired with a video, the Style Option overlay and the SHIFT+s panel of the big video overlay get a row that makes the song play the audio of its video file instead of its own. Per track; changed while the song plays, the audio is loaded again at once and goes on at the same time (pause and listening history stay); unpaired videos always play their own audio.
- The **Song:** line of the "Videos for the song" pane in the fetch videos overlay shows the song's length.
- The **Style Option** preview plays the track's video (small, in the space of the disk) while a row of the video block is selected, drawn like the video field with the track's effect, contrast, brightness, colours, chromatic aberration and rounded corners; without a video it stays the disk. The main screen behind the overlay stands still while it is open (as with the cover preview).
- **Fetch videos:** new `SHIFT+a` *Download only current selected* (the chosen video of the song under the cursor); `SHIFT+f` is now *Download all chosen (N)* with the number of choices; `CTRL+f` in the Songs and Videos pane has a fourth stop, *chosen* (only the songs with a chosen video); the legend has one more row (the panes are one row shorter). The found videos and all choices are saved at every change (`video_fetch_state.json`), so leaving the overlay without downloading loses nothing.
- **Marking text in input fields** now scrolls with the marking in both directions: with `SHIFT+←` / `SHIFT+HOME` the field follows the caret to the left (the marked text runs to its right) instead of staying on the other end; the caret column of the real cursor in the Settings fields is the caret's, not the other end of the marking. Also in the radio's fields.
- **Code structure (no change in behaviour):** the large functions (`handle_key`, `render_frame`, the settings screen, the meta data panel, `App::run`) are split into parts, the overlay rows are named constants, the state of READ LYRICS, cover fetch, creator, audio book, meta data editor and playlist editor lives in structs of their own (a change there no longer rebuilds everything), and the radio shares the history date helpers and two display helpers with the player. See `Changes_from_the_Original.md`.
- **Full screen video (the big video overlay):** the picture (and the oscilloscope / spectrogram beside it) keeps two empty columns to the left and right of it and is scaled down to fit, not cropped; the commands are two centred command rows (the first on the bottom border line, the second right below the box; what changes the picture / the panels and closing), the same at every terminal size and only worded shorter when the width needs it.
- **Meta data menu in Latin letters:** with the Latin letters switch on, the file name in the EDIT header, the values of the tag fields (when not being edited), the choices of a fetch and the file names of the cover / style overlays are shown in Latin letters like the lists (the text being edited stays as it is).
- **Translation editor:** a text pasted with the terminal (bracketed paste: `CTRL+SHIFT+V`, right mouse button) is one event now: its lines go into the rows like `CTRL+v`; with no text field open it is ignored (it used to be typed key by key, so letters triggered hotkeys and could open the help wizard). `CTRL+z` / `CTRL+y` undo and `CTRL+r` (or `CTRL+SHIFT+z`) redo up to 10 steps: a typed run in a line is one step, a deletion, a cut, a paste, a clear each another one (`CTRL+z` used to undo whole-line changes only, so typing could not be undone).

- **Paste over marked text:** pasting while text is marked in the translation editor now replaces just the marked text (a multi-line paste only fills the lines when nothing is marked).

- **Paste under Windows Terminal:** a paste (which Windows Terminal types in as keys) is now taken as one paste in text fields, so marked text or marked lines are replaced and pasted line breaks no longer act as ENTER line by line (translation editor, audio book note editor). Not tested on Windows here. The "paste multiple lines?" question is Windows Terminal's own setting.

- **Translations in the video views:** the translation in the big video overlay is shown in ( ) in the inactive lyrics colour, with no highlighting of its own (the sung words are lit on the lyric line only). The black box over the picture is now measured on the right line (it kept the size of an earlier line, which left long empty spaces at both ends of the lyric line). It uses the saved translations of the lyrics file edited last; TAB goes off → lyrics → lyrics + translation → translation only, through every saved translation. *Include Lyrics* (VIDEO SETTINGS, Settings, and *Use Lyrics on Video* in a track's Style Option) is now `none / lyrics / lyrics+transl. / transl.`, also in the small lyrics field: the translation uses the last row under the picture first, then the block grows upwards (the picture shrinks once for the whole track). `VideoLyrics=` takes none | lyrics | both | translation (true / false still work).

- **Read Lyrics:** the lyrics-files pane and the translation pane now sit side by side (three rows more for the text). `←` / `→` in the focused pane go through its entries and round the ends. New: `SHIFT+c` creates an empty translation file to fill in with `SHIFT+e`.

- **Big video overlay lyrics = the track's style:** TAB in the big video overlay now sets the track's own *Use Lyrics on Video* (Style Option), so the overlay and the small lyrics field always show the same (none / lyrics / lyrics+transl. / transl., and the same translation). The settings `VideoFullLyrics=` and `VideoFullTranslation=` are gone (old configs are read and ignored).
- **`j`:** `j` was free in the music player and the audio book, and is now **Cycle Play Mode Back** (`HKeyCyclePlayModeBack`, the opposite of `m`: five modes in the player, three chapter modes in the audio book); in the radio `j` also switches shuffle / list (it still means "down" inside lists and menus).
- **Menus organigram (`<`):** the boxes on the path from Main to the selection (Main included) have their border in the header colour; the branches on the path are in the header colour too, everything off the path in the progress bar's *remaining* colour; the boxes are narrower and a long row zigzags over two rows wherever the rows below have the space for it.
- **No lyrics fetch on the video view without a video:** with Video mode on and a track that has no video (also a stream), lyrics are fetched only when *When No Video Shows* is the lyrics; for a sphere / scope / spectrum / nothing no fetch runs and no "fetching lyrics" caption appears.
- **Disk Border (Settings -> ANIMA/VIZ -> DISK, off by default):** the ":  :" column between the disk and the meta data is left out unless it is switched on; the disk (or cover / book picture) then sits in the middle of the space between the left border and the meta data. Config: `ElimentDiskBorder=`.
- **Two songs with the same title no longer share a download:** the downloaded file is named after the title, so a second, different song called "Intro" played the first one's file. Mousiki now remembers which video id each file came from (`history/downloaded_audio_files.txt`) and gives another video of the same title its own file ("Intro [id].opus"). Files downloaded before (or outside Mousiki) keep their names and are trusted as before.
- **Code review fixes:** the "last used" view bookkeeping (`auto_prev_known_`) is only set together with the view it belongs to; the frozen screen behind the Style Option overlay and the cover fetch's scan flag are per App (music player / audio book) instead of shared statics.
- **Less work per frame (no change in what is shown):** the search for the video of a track without one (a folder listing and a pass over the library, until now on every frame of the video view) is kept per track for 2 seconds and dropped when a video connection or the library changes; the emoji check skips lines that cannot hold an emoji (braille, box drawing and block characters no longer take the slow path); the Hi-Fi bars reuse their buffers and do not analyse again when no new samples arrived (paused); the status file for `mousiki --status` is only rewritten when its content changed.
- **Idle mode and quieter waiting:** the main loop waits for the next frame on the keyboard (`poll()`, on Windows the console input handle) instead of 500 short sleeps a second, so a key press is handled at once and the CPU wakes far less. New *Reduce Motion When Paused* (Settings -> GENERAL -> TERMINAL, on by default, `ReduceMotionWhenPaused=`): paused or with nothing playing, on the main screen and with no key for 3 seconds, the screen is redrawn about 10 times a second instead of at the frame rate; any key brings the full rate back at once. 
- **Smoother video with looks (effects):** the per-pixel work of the video looks (scanlines, CRT, phosphor, halftone, dither, neon edge, film, gradient ...), the colour grade's chromatic aberration and the picture's Sixel colour reduction are shared between up to 4 threads (half of the cores) -- the picture is bit for bit the same as before, the heaviest looks were 25-35 ms per frame at *high* resolution; the CRT, phosphor and film vignettes no longer compute two powers per pixel. While a video is on the screen the screen is drawn at least 60 times a second (before, at the 30 fps setting a 25/30 fps film beat against the screen's rhythm and pictures were shown twice or skipped). `MOUSIKI_FX_THREADS=1` in the environment turns the threads off.
- **A cover picture that was edited in place is seen again:** the cover previews (meta editor, Cover Options, cover fetch) were remembered by file name only, so a picture replaced or edited under the same name kept showing the old one, and the disk's cover only changed after another choice. Pictures are now remembered together with their size and change time (looked at once a second), for the previews and for the track's own cover.
- **Disk/Cover/Thumbnail gets a fourth value, and the picture chosen for a track weighs most:** the VIDEO SETTINGS row (now also in Settings → ANIMA/VIZ → VIDEO) is *Disk/Cover/Thumbnail* with `cover`, `thumbnail`, `disk` (as before) and the new `thumbnail fallback` (the cover first, a frame of the video only for a track without a cover) (`VideoCover=cover|thumbnail|disk|fallback`). Choosing a picture in the meta editor's Cover Options makes that track show the cover at once, so the thumbnail or disk setting can no longer override it (Automatic gives the decision back to the settings); the Style Option row *Use Disk/Cover/Thumbnail* and the Cover Options group follow the same five choices. Tracks that were set to the plain disk keep it.
- **Slow frames are named in the console log:** a frame that took more than 40 ms to build, or more than 40 ms for the terminal to take (the write of the picture), while a picture is on the screen, adds a line such as `slow frame: built in 12 ms, the terminal took 85 ms for 412 KiB (picture 960x540)` (at most 2-3 lines a second; nothing at all while everything is fast). It tells a stutter of the video apart: Mousiki's own work (built) against the terminal swallowing the Sixel data (took).
- **A picture or video frame that could not be read is tried again:** the cover and video-frame previews (meta editor, cover and video menus) remembered a failed read for the whole session, so a file that was busy or half written at that moment (a download still running, a drive that had gone to sleep) kept saying "(the picture cannot be read)" until Mousiki was restarted. A failed read is now tried again after 5 seconds.
- **Any picture file for a track, and the reason when a picture cannot be read:** in the meta editor's Cover Options the search (`/`) accepts the full path of a picture file (typed or pasted) and lists it, so a track with no picture near it (a video in a download folder of its own) can still get a cover; the overlay says so when nothing was found. When ffmpeg gives no picture for a file, its complaint goes into the console log once (`picture: ffmpeg gave no picture for ...`).
- **The slow-frame line names the parts:** besides the time the frame was built and the time the terminal took, it now says how long the look (effects and colour grade), the colour reduction and the encoding of the picture took (`look 12 ms, colours 4 ms, encoding 9 ms`), so a stutter can be traced to one of them.
- **Videos in `video_down` find the download folder's covers:** a video downloaded into `<download folder>/video_down` also looks into `<download folder>/fetched_covers` (the covers fetched for the downloaded songs) for its cover: in the Cover Options list, by the album name in the automatic search, and for the cover fetch's "already have one" check. Other folders are unchanged.
- **Faster video looks:** the Game Boy optimizations now apply to the other looks too. The gradient looks work out the wave's brightness limit once per frame instead of per pixel (Gradient, Dither Gradient); the per-pixel `pow()`/`fmod()` calls are replaced by tables or cheaper exact arithmetic (Gradient, Phosphor, CRT, Dither); Halftone works out each dot once instead of every pixel; Bloom and Neon Edge sample their glows once per pixel for all three colours, Neon Edge works out its colour once, and Bloom, the grade (contrast / colours / brightness) and the shadow lift now run on the look's worker threads. Measured on one thread at 720x404: Bloom 30 -> 18 ms, Halftone 21 -> 10, Neon Edge 20-26 -> 13-19, Dither 9 -> 5, Dither Gradient 14 -> 10, CRT 13 -> 8, Gradient 13 -> 10. The pictures are unchanged except a handful of pixels per frame that can differ by one level (CRT, Gradient, Phosphor). Tested on Linux only.
- **Settings table (internal, nothing changes for you):** 67 settings (28 flags, 15 numbers, the 33 colours and two texts: the Use... views, the video flags, the visualizer speeds, all Color... lines, AudioDevice ...) are now one entry each in a table in `settings.cpp` (key, older key, range, comment) that drives both reading and writing; the file that is written is byte for byte the same as before. A number may now also be quoted (`VideoLayout="2"`), like the other settings. New tests: every flag, number and colour in config.txt is changed and must come back after a read and a write (`settings_every_simple_key_round_trips_with_a_changed_value`), and the old key names, ranges and flag spellings are checked.
- **Quitting ends the programs the player started:** at the end the player gives its background tasks a moment; one that is still waiting for a program it started (a download, the lyrics or translation helper, ffprobe on a slow drive) now has that program ended (`kill_all_children()`), so the task returns, the player closes in the proper way and nothing is left running on its own. Before, such a task kept the player alive until the process ended and the program went on running.
- **Settings table, second part (internal):** 15 more settings in the table: the six percent values (CoverContrast / Brightness / Colors, VideoContrast / Brightness / Colors: steps of 5, a trailing %), the box characters and the list separator (written between quotes), ColorLegendCommand, and the two colours that are only read. What the file accepts and what is written is unchanged (checked against the old code with the same inputs).
- **Settings table, third part, and background threads (internal):** six more flags are in the table (ElimentDiskBorder, TerminalDefaultFont, MarqueeScrolling, StereoPlayback, NormalizeVolume, EqualizerEnabled; 88 entries in all; the written config.txt is identical). The rest of the settings keep their own reading code on purpose: each has a rule of its own (a spelling, decimals, an older key). The name and kanji lookups, opening a web address and the update check ran on bare detached threads; they now run through `bg_async`, so quitting waits for them for a moment (and ends the program they run) like for the other background tasks. The radio's helpers (its `Ui` state, the text edit, the geometry check) moved out of `radio_main.cpp` into `radio_main_support.h`. A `.clang-format` is in the folder (closest to the existing style; use it for the lines you change: `git clang-format`).
- **Test suite:** a repeat of the whole UI suite with two busy processes (3 runs) found one more flaky check (organigram_menu: read the screen right after a key); it now waits for the expected text like video_fullscreen_sizes.
- **Preview of another track no longer blinks (Style Option, Cover Options):** the preview of a track whose disk shows a video frame (Thumbnail looks) and the playing track's own cover shared one slot, so asking for both every frame threw each one out again and again (the picture, the plain disk, the picture ...). The previews have a slot of their own now (`track_cover(rq, true)`; test: a_preview_slot_and_the_playing_slot_do_not_throw_each_other_out). This is one cause I could show in a test; whether it is the only cause of a blinking Cover behind Disk preview in a Sixel terminal I could not see here.
- **The cover no longer goes away while you change its look (Style Option):** every step of Look / Contrast / Brightness / Colors / Chroma (and the album look) counted as a change of the cover store, so the cover of the playing track was read again and was gone until the read was done (it stayed only for a track of an album with a tag). They now have a counter of their own (`cover_style_revision()`): the picture stays, only its drawing changes (test: a_style_or_look_change_does_not_make_the_cover_load_again).
- **The radio's main loop is a class now (internal, nothing changes for you):** `radio_main()` was one function of about 2,700 lines with 63 inner functions that shared about 50 variables. Those are now the members and methods of `RadioApp` (`src_radio/radio_app.h`): the set-up, the headless modes (`--dump ...`, `--selftest`) and the loop of frames in `radio_app_run.cpp`; tuning, the sleep timer and the windows in `radio_app_core.cpp`; the stations overlay, the browser and the station lists in `radio_app_stations.cpp`; the settings screen, themes and audio device in `radio_app_settings.cpp`; and the keys in one method per overlay or menu (`radio_app_keys*.cpp`; the longest one, the settings screen, has 413 lines). `radio_main.cpp` is 34 lines. To show that nothing changed, `tools/radio_compare.py` plays ~250 keys through every overlay and menu and records the screen after each (animated parts and numbers masked) and the files written: the old and the new binary give identical transcripts (253 screens, both the standalone radio and the radio mode of the main program), all `--dump*` outputs are identical, and the 1,334 UI checks pass. `MOUSIKI_RADIO_SEED=n` fixes the random choices of the radio (shuffle) for such tests.
- **Smaller clean-ups after that split (internal):** the radio's headless modes are one method each (`headless_dump`, `headless_selftest` ...) and the settings key handler is three (`key_settings`, `key_settings_theme`, `key_settings_edit`; the longest radio method is ~230 lines now, was 2,700). `tools/radio_compare.py` plays 93 more keys (theme picker, create theme, field editing, key re-binding, leave prompt): old and new binary still give identical transcripts (346 screens, standalone and radio mode of the main program), and all `--dump*` outputs are identical. `app.h` lost 11 small data types (rows, jobs, download state) to the new `app_types.h`; `App::PendingLoad` etc. still work (they are `using` names). Five more settings are in the table (ElimentDisk, ElimentQueue, ElimentWaveForm, ElimentLyrics, Visualizer, each with both older spellings: `Eliment_*`, `Element_*`); the rest read their own way on purpose (quoted numbers, decimals, own spellings: moving them would change what they accept). Two more UI checks that read the screen right after a key (organigram_menu, video_library_modes) wait for the expected text now; a repeat of the whole UI suite under load (3 runs, two busy processes) then had one more flaky check, which is fixed.
- **Idle CPU, measured and lowered:** measured on Linux with a 2-minute silent song (10 s per state): playing at 30 fps 2.6% of a core (29 screens a second, about 16 of 45 rows each, ~135 KB/s: the row diff was already there; what changes is the animation); paused with Reduce Motion When Paused 1.0% (40 wake-ups a second); paused without it 2.3%. A paused screen is the same frame after frame, so now, once 20 frames in a row (2 s) were exactly the same, the loop looks at the screen only 4 times a second (and waits on the keyboard in slices of 100 ms instead of 40): paused 0.5% and 16 wake-ups a second. A key, a change of the screen (a cover arriving, a new line) or a resize brings the 10 per second back at once; the slow disk of "nothing playing" still turns at 10. Windows not measured.
- **Radio idle CPU:** the radio had no resting mode at all: with no station tuned it drew 30 screens a second (the frame rate; 2.5% of a core, about 254 KB/s to the terminal). It now follows the player's Reduce Motion When Paused (`ReduceMotionWhenPaused=` in the player's config.txt, read when the radio starts): no station tuned (or failed / the timeshift paused), no key for 3 s, the help wizard closed -> 10 screens a second, and 4 once the screen stood exactly still for 2 s (the off-air satellite and the border wave keep moving, so in practice 10). Measured on Linux (null audio, 10 s): 2.5% -> 1.1% of a core, 254 -> 89 KB/s; a key brings the full rate back at once (the wait is on the keyboard, in slices of 50 ms). A tuned, playing station is not changed (it draws the visualizer at full rate). New UI check `radio_idle_rate`. Windows not measured.
- **Playing CPU, profiled (music player and radio):** measured on Linux with null audio and callgrind (instruction counts, which do not wobble with the machine's load the way CPU percentages do). Playing costs about 2.2% of a core in the player and 2.55% in the radio (a tuned test stream), at 30 frames a second, about 135 and 270 KB/s to the terminal. The audio threads are below 0.1%; the rest is the main thread building the frame (76% of it in the player, 85% in the radio), of which the FFTs of the spectrogram and the Hi-Fi bars are the largest part (about a quarter in the player, 40% in the radio): real work, and the spectrogram analysis runs on purpose while a track is loaded (so its history is there when it is opened), so they were left alone. Three things that were pure waste are gone, each with a test that compares the new code with the old one on the same input: the VOLUME BAR's disk look turned about 6000 points of a disc to light a 40 x 4 dot strip, twice per frame (13% of the player's main thread; now only the points that can land in the strip are looked at: 10 times less, `render_frame` 5.3 -> 4.5 M instructions); every frame searched itself twice from the start for a text-caret escape before it was written (11% of the radio's main thread; now one scan from the end: 8 times less); and the radio's gradient colours were formatted with three `to_string` calls each, 300 times a frame (now written into a buffer: 4 times less, the radio frame 5.4 -> 4.5 M instructions, 17% less). Not touched: the emoji check of the width helpers (about 5%; it already skips frames without emoji, what is left is string copies).
- **Startup and memory, measured:** the first screen is there after 0.22 s and the library listed after about 0.7 s with 1 and 2000 tracks, after 0.36 s / 0.91 s with 20,000 tracks (null audio, Linux, warm disk cache). Memory (RSS): 35 MB with one track, 42 MB with 2000, 90 MB with 20,000 (about 2.7 KB a track). A single track playing for 8 minutes: flat (108.0 -> 108.1 MB, 0.003 MB a minute, so no leak in steady playback); a run of very short tracks grows about 1.4 KB a track change (the played history), which is not a leak either. Windows and macOS not measured.
- **UI test `video_fullscreen_sizes`:** waits for the expected text (up to 8-15 s) instead of reading the screen right after a key, and no longer presses a key too often when the screen lags; it was the one check that failed now and then on a busy machine (6 of 6 runs passed with three copies and busy processors).
- **Cover loading no longer holds up quitting (internal):** the helper tasks of the cover loading and the picture previews (`bg_tasks.h`) run on detached threads instead of `std::async` (whose futures made the end of the program wait for a running ffmpeg), at most three ffmpeg runs go at the same time (scrolling through the picture list used to start up to 32), a preview that was scrolled out of the list is not started or read any more, and at the end the program waits up to 1.5 s for the tasks and then ends without running the destructors if one is still busy. The cover fetch already had its own cancel and join. The unit tests and the cover UI scenario also ran clean under ThreadSanitizer.
- **Build options for checking the code:** `-DMOUSIKI_TSAN=ON` builds everything with ThreadSanitizer (use a build folder of its own; the 350 unit tests and a video UI scenario ran without a report), `-DMOUSIKI_WERROR=ON` makes warnings in Mousiki's own sources errors (the sources currently build with no warnings under `-Wall -Wextra`). Both are off by default.
- **Dead look code removed:** the Bloom look (14) and the old Dither (11) had not been offered for a while (a stored setting of them already reads as Off / Dither B/W), so their drawing code is gone; the numbers stay reserved and do nothing.
- **Video frames are written by a writer thread:** a frame that carries a picture (32 KiB or more) is handed to a thread that writes it to the terminal while the next frame is built, so build and terminal time overlap (before, a frame cost their sum: with a slow terminal about 75-80 ms for 720x404, now about the larger of the two). Everything else that writes to the terminal waits for the writer first, so the order never mixes. `MOUSIKI_SYNC_WRITE=1` (environment) turns it off. The slow-frame log line now says how long the picture waited for the writer and how long the terminal took for the last frame. Tested on Linux only.
- **Thumbnail choices show their frame:** in Cover Options (meta data menu) the preview of *The video thumbnail, else the cover* shows a frame of the track's video, and *The cover, else the video thumbnail* shows it when the track has no cover.
- **Files outside the library find the library's fetched covers:** a track or video that lies outside the library folders (the download folder's `video_down`, the cache, any other place) now also finds the covers in the `fetched_covers` folders inside the library folders, by album name, in the Cover Options list, the automatic search and the cover fetch check. The folders are indexed in the background (at most once a minute, again when the library folders change). Tested on Linux only.
- **The video decoder yields to the picture:** after every start (a seek, a switch between the main screen and the big video overlay, a new picture size) ffmpeg decodes flat out to fill its buffer for a second or two, and took the processor away from the drawing of the picture: the effects took 3-4 times longer for the first frames (measured in a console log: 120-140 ms against 30-40 ms). The decoder now runs at a lower priority (nice 5 on Linux / macOS, below normal on Windows), so the picture goes first; in a test with an effect running next to a flat-out ffmpeg the frame time rose by 45 % before and by 15 % now.
- **A paired video shares the cover world of its song:** a video file that is paired with a song (a link, a Search YT download / mp3 conversion, or the same file name in the library) takes the cover chosen for the song, the pictures in the song's folder, its `fetched_covers` and the picture inside the song when the video has none of its own (the video's own choice goes first), in the disk, the meta editor's cover pane, the Style Option preview and the Cover Options list. The pairing is only a link: a song that was deleted still serves its choices to the video, and deleting a video leaves the song untouched.
- **New look "Game Boy Low-Res Gradient"** (`VideoFx=game boy low-res gradient`): the big blocks of Game Boy Low-Res with the shades in the gradient wave's colours, the counterpart of Game Boy High-Res Gradient. It sits right after Game Boy Low-Res in the lists.
- **The Game Boy looks are cheaper to compute, the picture is bit for bit the same:** the colour of a block is worked out once instead of for every pixel of it, the wave's brightness reference is worked out once per picture instead of once per block, and the blocks are shared between threads like the other looks (checked against the earlier code for all five Game Boy looks, three picture sizes, with and without braille, two times).
- **The slow-frame line splits the look further:** `look 54 ms [grade 12, effect 20: 38, threads 2]` -- the colour grade and the effect (with its number) apart, and how many threads the looks used.
- **`App` state grouped into structs (internal, no change in behaviour):** the loose data members of the `App` class that belong to one feature (cheat sheet, sleep timer, equalizer, wizard, marquee, kanji, waveform, search, spectrogram, bulk add, quick-track-pick, folders, themes, phone, video manager / library / search, read lyrics, audio devices, converter, video fetch, queue, lyrics, graphics, devices, current track) now live in nested structs (`cheat_.query`, `theme_.sel`, `cv_.scroll`, ...), 25 groups, about 2,900 uses renamed mechanically and then checked by the compiler. Where a group's natural name was taken by an older member, the new struct member is `vfs_`, `qst_`, `gfxs_`. Nothing was moved to another place in memory that is read in a loop, so frame cost is unchanged by construction (a member of a struct is the same fixed offset as a loose member); not re-profiled. Checked: 361 unit tests, the 1338 UI checks, and `tools/app_compare.py`, a new tool that plays ~420 key situations of the music player (menus, overlays, settings, queue, lyrics, themes, video fetch ...) and writes every screen to a transcript: the transcript of the new binary equals the one of the batch-227 binary except for one or two lines whose content depends on timing (the lyrics helper's message, which also differs between two runs of the same binary). Windows (MinGW) syntax check not run for this change (no MinGW in the build container), Windows and macOS not run.
